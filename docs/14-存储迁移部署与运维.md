## 数据、key 与失败状态

D1 表包括 libraries、assets、blobs、categories、tags、asset_tags、uploads、upload_parts、pairings、devices、imports、jobs、audit、garbage、rate_limits。原始 X cookies、headers、tokens 和浏览器配置没有对应字段。

- 视频 key：`v1/libraries/{opaque_library_id}/media/{random_transfer_id}/video`。格式/mime、SHA-256、大小在 blobs/D1/R2 元数据保存，不以文件后缀证明内容。
- 海报 key：`v1/libraries/{opaque_library_id}/posters/{asset_id}/{random_id}`。更新先登记孤儿回收，再写对象和元数据；旧海报进入垃圾队列。
- key 永不复用。相同资料库 SHA-256+size 的内容复用 blob；相同来源 post/media 复用 asset；跨资料库不暴露命中情况或共享可访问 key。
- 上传状态：uploading → completing → verifying → ready；中途取消/失效为 cancelled 或 failed。对象写成功但校验/发布失败不生成可见 asset。
- 接力状态：fetching → ready/failed；幂等键同时绑定 device、library 和规范化请求哈希。相同 key 改正文 409；仍在获取中返回 202，不能删掉正在工作的 reservation。
- 任务状态：queued → claimed → ready/failed/cancelled。领取产生新的 lease_id，过期再领取会终止旧租约传输；晚到 complete 无法发布。
- 上传完成、设备有效性、来源和任务 lease 的判断在同一 D1 batch 内；删除同步移除 asset 和无引用 blob 元数据，R2 字节随后清理。

R2 multipart 最后一步失败时按 upload status 重试；原始 part 先在 D1 预留 SHA，重传同片不同字节 409，防止先覆盖 R2 再发现冲突。浏览器进度区可暂停/重试；24 小时内重新选择同一文件可恢复已确认分片。R2 multipart 的上传与完成能力以官方 API 为准。[2]

## 生命周期和删除

- 已配置 `snail-abort-incomplete`：全部前缀，未完成 multipart 一天后自动终止。R2 原有默认七天规则未被修改，更短 Snail 规则起保护作用。
- 上传 24h 到期；接力 fetching 超过 10min 失败；失败/取消对象延迟至少 5min 入清理队列，避免与正在终止的请求竞争。
- 每小时清理最多 100 个到期垃圾 key，只有 D1 中没有 live blob/poster/活动传输引用才删 R2。过期 multipart 每轮最多 50 个，Cloudflare 生命周期补偿 D1 写入前崩溃的孤儿。
- ready 上传记录保留 7 天，imports 30 天，已完成/取消 jobs 与 audit 90 天；到期 pairing 和限流记录定期回收。设备记录供用户撤销/审计，不自动等同删除作品。
- 用户删除立即从列表与 API 消失，物理字节按上述清理节奏回收；无回收站和产品内撤销。版权投诉/授权撤回时，从库中删除并核对对象回收。发布测试资产也按同样路径删除。

删除不保证已下载到用户设备的副本消失；作品保留和传播须由使用者根据真实授权决定。[3]

## 配额与成本边界

实现额度是每视频 512 MiB、分片 8 MiB、海报 2 MiB、单库 50 GiB、最多 5 个活跃上传/接力、最多 200 个排队/领取中 job。用户 API 默认 600 次/分钟，设备 API 120 次/分钟，配对创建/轮询独立限流。超额明确 409/413/429，不自动扩容或开公共桶。

这是应用保护额度，不是 Cloudflare 的计费上限；存储 GB-month、R2 读写、D1 行读写、Worker 请求与定时清理分别计量，实际套餐和账单应查看 Cloudflare 控制台。[4] 不在代码中承诺“永久免费”。个人规模优先保持这个简单架构；长视频、批量转码或多用户共享需要重新做资源测量。

## CI/CD 与发布

`CI` 包含 typecheck、Biome 推荐规则、合成 ffmpeg fixtures、Vitest/workerd/D1/R2、Playwright Chromium desktop/mobile、研究哈希、品牌哈希、Vite build、Worker dry-run、gitleaks 和 OSV。依赖锁文件和 Bun/Node/Wrangler 固定版本；上游 reusable workflows 固定到 `ad43150de3a2be2fa464b5cd2f921dc4fa9f8f0f`。

`Release` 仅消费经过证明的成功 CI run，要求 main 的实际 source SHA，随后应用 D1 迁移、部署 Worker，并运行公开生产探针。生产串行锁为 snail-production。PR 不拿生产凭据；Access 配置不交给 CI。公开 AUD 和研究中的字面量 R2 key 使用精确 gitleaks 例外，没有关闭整个规则或研究目录。

GitHub Environment `production` 存储 `CLOUDFLARE_API_TOKEN` 与 `CLOUDFLARE_ACCOUNT_ID` 两个 Secret；account ID 本身公开，同时保留同名 Variable 供配置参考，但共享部署工作流要求从 Secret 读取。调用方不选择 Environment，因此不尝试在调用阶段解析它的值；由共享工作流的 production job 直接取得，未使用 `secrets: inherit`。新建 `Snail production deploy` token 的权限仅为账号 Workers Scripts Edit/D1 Edit/R2 Storage Edit/Account Settings Read，以及 hexly.ai Zone Read/Workers Routes Edit。不含 Access Edit；不可用短期 Wrangler OAuth 替代长期 CI 凭据。[5]

```sh
bun install --frozen-lockfile
bun run types
bun run research:check
bun run brand:check
bun run check
bun run test:e2e
# 已认证的本机发布方式；第一次先有新建的独立 Access 应用和 AUD
bun run deploy

# main 已 push，CI 和 Release 都成功且与当前 SHA 一致之后

# 标签/Release 只针对通过检查的真实初版版本；后续 release 先更新 package.json
```

当前工程的开发预览使用 `bun run build && node scripts/test-server.ts`，只绑定 127.0.0.1:4173，临时签名身份和内存测试库，重启后不保留资料。它是本地开发/测试代理，不会进入 Worker 或部署包；生产代码不接受测试身份头。普通 Vite 开发服务只提供前端，API 联调应使用上述完整预览。

## 恢复与运营

迁移按 migrations 顺序追加，不重写已经应用的 SQL。先备份生产 D1 并记录当前 Worker version ID，再执行具有数据风险的未来迁移；不要自动清空表或覆盖桶。本版 0001 建库、0002 增加租约/传输字段，已在真实 workerd 与远程新库执行。未来已有数据的破坏性迁移需单独回归，不以这次空库迁移代替。

Worker 回滚使用 Cloudflare 已发布版本恢复流程；数据库不随 Worker 自动倒退。D1 的恢复/导出和 R2 备份需要另行保存并校验，不能只备份代码仓库。[6] 恢复时以 D1 引用为准核对 R2 key/大小/哈希，暂缓 GC，避免把恢复中的对象误判为孤儿。未提供“自动备份已完成”的承诺。

`/api/live` 匿名必须 200 application/json、status=ok、顶层 version、no-store；数据库或桶不可用应非 2xx。根路径和用户 API 应 302 到 Access；设备 heartbeat 没凭据应 401 JSON，不能跳转登录。实际 Access 应用 path `api/live` 也覆盖尾斜杠和后代路径：`/api/live/`、`/api/live/child` 被 Worker 精确路由拒绝为 401 `authentication_required`。因此公开范围的最终边界由 Worker 的精确 path + GET/HEAD 实现，不能仅凭 Dashboard 的 path 字面量推断。`bun run production:check` 验证两层组合后的行为，后代路径可以由 Access 302 拦截或 Worker 401 拒绝，但不能公开成功。网络失败保留原结果并有界重试；不把 Access 登录页或旧版本缓存算作健康。
